# Self-hosting

[← Back to Hitchhike](../README.md) · [Run locally first](development.md#run-the-dashboard-locally)

Your relay runs as one Cloudflare Worker with its own D1 database. That Worker serves both the dashboard and API using the same relay core as hosted Hitchhike. You need a Cloudflare account, Node.js 22.16 or newer on the 22.x line or Node.js 24 or newer, and your own owner and encryption secrets. You do not need Clerk, Vercel or a hosted Hitchhike account.

Start with the [isolated local checks](development.md#run-the-checks), then verify your own deployment with a harmless handoff.

## Create your configuration

If you need to install Node.js first, start with the [development prerequisites](development.md). Clone the repository, install dependencies and copy the example configuration:

```bash
git clone https://github.com/davidspiegs/hitchhike.git
cd hitchhike
npm ci
cp wrangler.selfhost.jsonc wrangler.selfhost.local.jsonc
npx --no-install wrangler login
npx --no-install wrangler d1 create my-hitchhike --config wrangler.selfhost.local.jsonc
```

Choose a unique Worker/database name instead of `my-hitchhike` if needed. Edit `wrangler.selfhost.local.jsonc`:

- Set `name` to your Worker name and `database_name` to the database you created
- Copy the returned `database_id` into the D1 binding; keep its binding name `DB`
- Set `PUBLIC_URL` to your exact HTTPS Worker origin, such as `https://my-hitchhike.YOUR-SUBDOMAIN.workers.dev`, or your configured custom domain
- Set `RELAY_NAME` to the name you want in your dashboard
- Keep `HOSTED=false` and `ALLOW_DEV_AUTH=false`

Find your Workers subdomain in your Cloudflare account’s Workers & Pages settings. If you use a custom domain, configure that domain for your Worker as well; setting `PUBLIC_URL` alone does not create a domain route. The copied configuration is gitignored. Use its path consistently in every command, so your database and secrets belong to your relay.

The default `wrangler.jsonc` is also an example self-host template.

## Set secrets and deploy

Generate two different high-entropy secrets in a password manager: one for `ADMIN_TOKEN`, one for `ENCRYPTION_KEY`. Alternatively, if OpenSSL is available, run this command twice and save each generated value separately in your password manager:

```bash
openssl rand -base64 32
```

Paste each saved secret at the matching prompt:

```bash
npx --no-install wrangler secret put ADMIN_TOKEN --config wrangler.selfhost.local.jsonc
npx --no-install wrangler secret put ENCRYPTION_KEY --config wrangler.selfhost.local.jsonc
npx --no-install wrangler d1 migrations apply DB --remote --config wrangler.selfhost.local.jsonc
npx --no-install wrangler deploy --config wrangler.selfhost.local.jsonc
```

These commands create secrets, migrate the remote database and deploy in the Cloudflare account you selected. If wrangler reports that the Worker does not exist yet, accept its offer to create it; the Worker answers 503 "setup required" until both secrets exist. `npm run db:selfhost:remote` and `npm run deploy:selfhost` are shortcuts for the two `--config wrangler.selfhost.local.jsonc` migration and deploy commands. Use your own configuration and check the target shown by Wrangler before continuing.

Keep both secrets in your password manager. Public self-hosted deployments require distinct `ADMIN_TOKEN` and `ENCRYPTION_KEY` values of at least 32 characters, and reject known sample values; otherwise the relay returns a configuration error. The encryption key protects recoverable connection credentials; losing it can require reconnecting agents. Do not rotate it casually. `.dev.vars` is local configuration, not a way to upload production secrets.

For optional approval notifications, set `OWNER_NOTIFY_URL` to an endpoint you control. In the self-hosted `default` workspace, the relay sends a best-effort plain-text POST for approval-gated tasks, with `Title: Relay: approval needed`, sender/receiver IDs, task type/title and a dashboard review link. The endpoint receives that task metadata. Notification failures time out after five seconds and have no durable retry; the dashboard remains the place to review waiting approvals. Hosted mode does not use this setting.

## Verify your first handoff

1. Open your relay’s `PUBLIC_URL` and enter its `ADMIN_TOKEN` in the **Owner key** field
2. Create a sender and a receiver in the dashboard
3. Follow your dashboard’s generated setup instructions in each agent
4. Send a harmless task, have the receiver pick it up and return a result, then retrieve it from the sender
5. Verify connection revocation before enabling recurring work

Use [the connection guide](../adapters/README.md) for authentication and pickup details. Self-hosted mode has no OAuth flow: clients use a connection's bearer credential or the private `/mcp/<key>` URL generated by your dashboard. Prefer authorization headers where supported; URLs containing keys can appear in logs or shared histories.

`GET <PUBLIC_URL>/healthz` returns `{ ok, protocol, release, version }`. `version` is Cloudflare's version id for the running Worker deployment, read from the `version_metadata` binding in the template. `release` is `null` unless you stamp a deploy yourself, for example with the release tag you checked out: `npx --no-install wrangler deploy --config wrangler.selfhost.local.jsonc --var HITCHHIKE_RELEASE:vX.Y.Z`; values are limited to 64 characters of letters, digits, `.`, `_` and `-`. `/terms` and `/privacy` describe the maintainer's hosted service only; a self-hosted relay returns 404 for both, and its dashboard does not link them.

The five-minute cron maintains leases, schedules and retention. It does not start an AI app or keep an agent running. Any recurring worker needs its own authorized runner or provider-supported schedule.

## Upgrades and recovery

Releases are published to the public repository as squashed snapshots, one commit per tag, so there is no commit-by-commit history to read. To upgrade:

0. Fetch the latest release tag and check it out: `git fetch --tags && git checkout vX.Y.Z`. Compare the `migrations/` directory between your current tag and the new one, for example `git diff --stat vA.B.C vX.Y.Z -- migrations/`, to see which migrations are new.
1. Export the database and keep a copy of the deployed source/configuration before applying migrations. For example, use `wrangler d1 export DB --remote --output <backup.sql> --config wrangler.selfhost.local.jsonc`.
2. Rehearse the upgrade against a separate staging database; run the local suites against the candidate code.
3. Apply migrations **before** deploying the corresponding code. Migration `0003` preserves existing data under the `default` workspace and replaces some table/index structures.
4. Verify login, existing connections, one handoff, result retrieval and credential revocation after deployment.

Migrations are forward changes; reverting a Worker deployment does not revert its database. Rehearse recovery from an export or Cloudflare D1 Time Travel before public launch. Backup retention and deletion timing must be communicated for the account's actual plan, not assumed from the application's history setting.

After enabling Clerk, do not deploy a pre-Clerk Worker against the populated database. Older versions do not enforce the new provider/session boundaries or pending account-deletion markers. Setting `AUTH_PROVIDER` on that older code does not add those protections. Use a compatible patched Worker, or recover a coordinated database/source backup in an isolated environment and validate its access controls before routing traffic to it.
